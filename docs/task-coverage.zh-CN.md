# 任务覆盖与持续开发

当前以维护者批准的研究产出计划为优先：复用已有结论、诊断具体失败、积累有条件的场景／solver 经验。AI 试参属于方法，覆盖表描述范围。见[诊断](site/zh/diagnosis.md)与[选型](site/zh/selection.md)。**定时开发保持暂停**；下文资源和证据规则保留。

**我们更看重一个引擎能可靠完成多少种任务。** 每种任务可选择适合的 solver 与参数，同时展示物理误差、稳定性和成本。重复实验、步长扫描、换用框架都不增加任务类型。

## 一份清单，双语详细展示

`docs/task-coverage.json` 是版本化清单。更新证据后运行 `python scripts/task_coverage.py`；`--check` 检查 双语详细覆盖页面是否过期，已加入双语严格构建。固定任务 ID 区分被动预折叠下落、机器人夹布抬升、主动折布。每行标明核心、solver、运行路径、版本与批次，并逐项记录全部任务。分表只是为了阅读，不改变统计分母。

每个单元格链接原报告（含命令和原始数据入口）或恢复 Issue。已运行结果与“不支持”必须有仓库内证据及 SHA-256。历史布料计数由全部 105 条冻结摘要重算；重复、遗漏、相互矛盾的记录会使检查失败。这是清单核对，不是完整轨迹重评分。缺失的历史参数读回继续保留缺失，改文档不能填补它。

历史批次单独展示，不计入新 `coverage-v1` 的可靠覆盖。该协议是验收约定，不表示已执行实验。新对照先冻结开发集、留出集和相同调优预算。合格单元格必须附带有哈希的独立验收报告，明确协议、任务、核心、solver、运行路径、版本，并完整通过正例、负例、独立物理评分、冻结留出、相同调优预算及来源核验。准入前连接底层协议、原始记录、评分、资源回执和已部署证据入口。生成器检查报告契约，审查者仍需核实底层证据。引擎总数取合格配置的**任务 ID 并集**；部分通过、失败、受阻、不支持、未运行都不计入。目前尚无配置按此新约定准入。

## 资源与恢复

旧 `experiment`（16 GiB／2 核）和 `experiment-24g` 保留供复现。新批次用 `bounded_run.py --profile adaptive --resource-plan BATCH.json`：未知负载从 16 GiB 开始，复杂模型加 `--complex-model` 从 24 GiB 开始；提供 `--peak-receipt PREVIOUS.json` 后，选 8／16／24／32／40 GiB 中至少为实测峰值 1.5 倍的最小档。每次启动另检查整档内存外还有 8 GiB 可用余量，保持零 swap 和现有磁盘／I/O 准入。CPU 从 4 核等效配额起，确认 CPU 瓶颈后可用 `--cpu-cores 8`。批次中复用相同计划参数，调资源要新建批次计划；不覆盖回执或冻结计划。

线程与进程共用 cgroup 的任务数上限，既有配置保留 128。若回执的 `pids.events` 证明该上限阻止框架初始化，可用 `--task-limit 256` 选择单独的自适应配置，并在新计划中冻结上限；CPU 配额和内存额度不随之增加。原生框架调查由 [#152](https://github.com/huangkiki/Dexlab/issues/152) 跟踪。内核提供 `pids.peak` 时回执记录实测峰值，缺失时保留 null。导入或转换成功不等于物理任务准入。

回执记录内存峰值／事件、CPU 限流、内存／CPU／I/O 压力及抽样显存。无法获取的 GPU／PSI 记为 null，不伪造为零。显存约每 10 秒抽样整卡占用，不是进程独占值或精确峰值。服务成本含监测开销，不等于纯 solver 吞吐。暂时保留原读写限速，先检查 I/O 等待再调整。隔离验证通过后，正确性实验最多两个独立进程；性能测量独占，并暂停传输和大规模哈希。

开发诊断采用可追加的六小时工作包。#143 下一包最多 64 次启动，保留旧 46 次账本与全部失败。新包必须有新证据、明确假设、冻结工况和独立账本，不再因旧 48 次上限反复等待批准。正式批次六小时／700 次单独计账。中断后根据真实进程、源码身份及回执恢复；回执不完整不算成功。

保持单个开发执行者：恢复在途工作，解决可行动阻塞，实现并独立验证，合并后核实部署版本，再更新覆盖并继续。复用每小时恢复心跳，仅在交付、重要失败或确需外部输入时通知；心跳不启动重复执行者，不无证据重复实验。
